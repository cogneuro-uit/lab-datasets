# Lab dataset catalog entry

The $lab_name keeps a catalog of every dataset it has collected at $catalog_url. Each dataset is
one YAML file. Your job is to help the user produce a **valid** file for one dataset and
to get it into the catalog. The catalog holds metadata and links only, never data and never
personal data about participants.

Always work and write in English, even if the user's material is in another language.

## Files in this skill

| File | Use |
|---|---|
| `reference/schema.json` | JSON Schema of a dataset entry (generated by the catalog app) |
| `reference/people.yaml` | Lab members: `id`, `name`, `slack_handle`. Use the `id` for `contact`/`contributors` |
| `reference/modalities.yaml` | The allowed modality ids |
| `reference/tags.yaml` | Existing tags (new tags are allowed) |
| `reference/datasets.yaml` | Datasets already in the catalog (`id`, `title`); ids must not clash |
| `reference/example.yaml` | A complete, fictional example |
| `scripts/validate.py` | Checks a file: `python scripts/validate.py <file>.yaml` (needs PyYAML) |

These lists were exported on $generated. If a person is missing from `people.yaml`, they
must be added in the web app (People page) before the file can be imported.

## Workflow

1. **Collect what the user already has.** Ask them to paste or point you to anything useful:
   notes, a study protocol, an ethics/REK application, a data management plan, a paper.
   Extract what you can from it before asking questions.
2. **Ask for the rest, a few questions at a time**, in this order (it mirrors the web wizard).
   Skip what you already know. Everything except section A is optional, so accept "don't
   know" or "later" and move on.
   - **A. Basics (required):** title; contact person; status; year the study started.
   - **B. People and time:** other contributors; when data collection started and ended.
   - **C. Content:** modalities; number of participants; population; task/paradigm; tags.
   - **D. Storage:** every place a copy lives (Teams/SharePoint link, server path, OSF, …),
     with a short note, and which copies are backups.
   - **E. Ethics and sharing:** sharing level; REK reference; Sikt reference; what
     participants consented to; a deletion date if the approval sets one.
   - **F. Outputs:** DOIs of publications and preprints; code repositories; related datasets.
   - **G. Notes:** anything else (known problems, excluded subjects, file formats).
3. **Write the file** as `<id>.yaml`, following the rules below and the field order of
   `reference/example.yaml`.
4. **Validate:** run `python scripts/validate.py <id>.yaml`. Fix every error and re-run until
   it passes. Mention warnings to the user (e.g. "no backup copy is marked"); they don't block.
   If you cannot run scripts, check the rules below by hand.
5. **Hand over:** tell the user to import the file at $catalog_url/new/import (upload or
   paste). The import page checks it once more before anything is saved. Give a short summary
   of what is still missing, so they can fill it in later via "Edit" on the dataset page.

## Rules for a valid file

**Required:** `id`, `title`, `contact`. Strongly recommended: `status`.

- `id`: `YYYY-short-name`: the year the study started, then 1–4 lowercase words joined by
  dashes, e.g. `2019-eeg-attention`. Only `a-z`, `0-9` and `-`. It must not already be in
  `reference/datasets.yaml`. It never changes later, so suggest it to the user and let them
  confirm. The file name is the id plus `.yaml`.
- `title`: descriptive, at least 3 characters, e.g. "Sustained attention and mind-wandering, EEG + pupil".
- `status`: one of `planned` (not started), `collecting` (data collection ongoing),
  `analysing` (collected, being analysed), `published` (results published), `archived`
  (finished and stored away). Do not use `retired`; that is done in the app.
- `summary`: 2–4 sentences on what was done and why. Markdown allowed.
- `contact` and `contributors`: person **ids** from `reference/people.yaml`, never names.
  Match names the user gives you to ids, and ask if a match is unclear (several people with
  the same first name, nicknames). Do not list the contact again as a contributor.
- `collected.start` / `collected.end`: `2019`, `2019-02` or `2019-02-15`. Leave `end` out
  while collection is ongoing.
- `content.modalities`: ids from `reference/modalities.yaml` only.
- `content.n_participants`: a whole number (participants in the final dataset, if known).
- `content.tags`: lowercase, words joined by dashes (`mind-wandering`). Prefer existing
  tags from `reference/tags.yaml`; add a new one only if nothing fits. Use 2–6 tags.
- `legal.sharing`: `open` (anyone, e.g. public on OSF), `on-request` (researchers who ask),
  `internal` (lab only), `restricted` (special limits from the consent or approval).
- `legal.delete_by`: a full date, `2034-12-31`.
- `locations`: a list. Each item has `kind` (`teams`, `server`, `osf`, `zenodo`,
  `openneuro`, `figshare`, `other`) and either `url` (web links) or `path` (server folders),
  plus optional `note` and `is_backup: true`. One entry per copy.
- `outputs.publications` / `outputs.preprints`: each item has a `doi` (bare form,
  `10.1234/abcd`, no `https://doi.org/`) and, if you know them, `title`, `authors`
  ("Doe, J., Mittner, M."), `venue`, `year`. The catalog can fill in the details from the
  DOI, so a correct DOI alone is enough.
- `outputs.code`: items with `url` and optional `note`.
- `outputs.related_datasets`: ids from `reference/datasets.yaml`.
- Leave a field **out** when it is unknown. Do not write empty strings, `null`, `TBD` or
  placeholders. Unknown fields are not allowed (see the schema).

## Never invent facts

Only write what the user told you or what is in their material. In particular, never guess
DOIs, URLs, server paths, REK/Sikt numbers, participant numbers or dates. A shorter, correct
entry is better than a complete-looking wrong one; missing fields can be added later.

## No personal data

Do not put participant names, IDs, health information or other personal data in the file.
`notes` may say "subject 7 has noisy EEG" (pseudonymised codes are fine), nothing more.
